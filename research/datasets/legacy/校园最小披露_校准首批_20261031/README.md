## 2. 已经记下的三项决定

这些决定已经实现。这里只留记录，避免以后再问一遍。

### 决定 A：按边界分开，共用一套规则核心

模型输入默认最小披露，优先用稳定代号、泛化或本地汇总。最终用户能看，不等于外部模型可以收原文。

结果展示按实际查看者的权限决定保留或恢复。没有授权不得恢复。

工具外发要重新检查接收方、用途和权限，不沿用展示边界已经放过的结果。

三者共用信息识别、任务必要性和硬权限约束，但分别做决定、分别记录、分别统计泄露。这仍然是一次必要性判断，不是三套互不关联的判断模型。展示边界放过的内容，不自动带到外部模型或公开外发。

### 决定 B：五类没有旧模板的工作只补最小规则

通知、统计、纪要、对外介绍这四个现有模板和测试都保留，`tasks.yaml` 没有改。

班级值日、课程成绩、辅导员交接、困难补助、宿舍报修只补了任务目标、必要字段、接收对象、授权条件和禁止披露项。学生活动、社团名册、纪要统计继续复用已有任务差异，不另写一套模板。

目标是覆盖八类校园协作，不是用八套固定模板做机械匹配。新规则已放进规则基线和后续对照，不预设它们会提高准确率。规则表只保留任务差异，不再为新场景追加固定匹配；后续判断仍靠任务感知的必要性，不靠把规则库越做越大。

### 决定 C：只要大致量级时用泛化

任务只需要高低时，在本地把准确金额写成「数百元」「数千元」「约一万元」这一类说法，再交给外部模型。不传原始金额和明细。

任务明确要求精确核算，并且接收方有权限时，才在对应的授权边界保留精确金额。外部模型和公开外发不因这个理由保留原数。

原文看不出量级时不编造；只有缺了它就完不成任务，才追问。泛化后的说法仍要保住任务需要的成本高低。这个处理记成泛化，不记成删除、汇总或追问。

## 4. 当前在线能力与离线规则的区别

在线入口目前是：

- `activity_notice`：原有活动通知模板，在线必要性模型可以处理。
- `class_coordination`：班级值日这类协作。只是允许用这个任务键进入现有在线流程，没有新模型。
- `contact_notice`：只处理「负责人 + 电话」这一则联系通知的占位和授权恢复。不经过必要性模型重训，也不调用云端。

课程成绩、辅导员交接、困难补助、宿舍报修、学生活动、社团名册、纪要统计仍只有离线规则结果。把这些任务键提交到在线入口会因未知任务暂停。离线规则通过，不表示在线功能已经完成。

在线动作由必要性模型选择，硬约束只放行或暂停。离线规则对班级协作的外部姓名是稳定代号。在线模型可能选择泛化。同一次处理里有两个及以上不同姓名时，泛化文本改用原有「人员甲」代号，避免都变成「某同学」后分不清谁负责什么。只有一个人时仍写成「某同学」。代号能不能恢复，仍看身份和接收方是否都允许，稳定代号本身不是授权。

GLiNER 权重缺失时，默认入口暂停。词典测试模式可以跑到本地转换，结果标明未验证，并且在外发前暂停。没有 API 密钥时不调用云端模型。电话、邮箱、宿舍的可逆编号没有实现。
