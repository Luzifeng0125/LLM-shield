## 一、系统架构（一眼看懂）

### 1.1 只有一个入口，一条主干

整个系统**只有一条主干**，从浏览器到云端：

```
浏览器 (web/index.html + chat.js)
   │  POST /api/chat/{id}/messages
   ▼
llm_shield/server.py ── FastAPI，只做「收参数 → 转交 → 返结果」
   ▼
llm_shield/chat.py ──── 会话状态（多轮历史、代号映射、20 轮上限、30 分钟过期）
   ▼
llm_shield/pipeline.py ─ 端到端编排（真正的主干，291 行）
   │
   ├─ m1_access   权限：这个身份能不能读这份材料 / 能不能发给这个接收方
   ├─ m2_detect   识别：找出敏感片段          ← 唯一的「模型密集区」
   ├─ m3_decide   决策：选六种动作之一
   ├─ m4_necessity 动作模型：给六个动作打分    ← 第二个模型（TF-IDF+逻辑回归）
   ├─ m5_utility  效用：这样处理后任务还做得成吗
   ├─ m6_transform 转换：删除/聚合/泛化/代号替换
   ├─ m7_egress   外发：三边界检查 + 调云端 API
   ├─ m8_audit    审计：记录每次外发
   └─ m9_data     数据：合成训练语料（**离线工具，不在运行链路里**）
```

**关键理解**：`pipeline.py` 是唯一把九个模块串起来的地方。看代码只要先看它，
就知道每个 mX 模块在什么时候被调用、输入输出是什么。

### 3.4 识别器重叠矩阵 —— 4 个实现干着同一件事

| 识别器 | 覆盖类别 | 常驻? |
|---|---|---|
| `regex_rules`（正则+校验位） | 10 类（格式类） | ✅ 常开 |
| `entity_rules`（词典+上下文） | 4 类（人名/机构/地点/敏感属性） | ✅ 常开 |
| `campus_ner`（RoBERTa，388 MB） | 12 类 | ❌ 默认关 |
| `gliner_ner`（GLiNER，1.13 GB） | 14 类 | ❌ 默认关 |
| `reviewed_ner`（BERT） | 14 类 | 只在 GitHub 仓库里，工作目录没有 |

**重叠实况：**

- `campus_ner ∩ gliner_ner` = **12 类** ← 两个完整 NER 模型，干几乎同一件事，且同时只能开一个
- `gliner_ner ∩ regex_rules` = **10 类** ← GLiNER 若按 13 类跑，会把正则已做好的格式类再算一遍（这正是我上轮把它收窄到语义 5 类的原因：收窄后独立集 F1 从 0.8383 升到 0.9068）
- `entity_rules ∩ gliner_ner` = **4 类** ← 词典和 GLiNER 抢同一批语义实体（`pipeline.py` 已用 `detect_org_location=not use_gliner` 让词典在 GLiNER 开启时让位）

`build_detectors()` 实测挂载结果：

```
默认(不改 .env) : ['regex', 'entity']
开启 GLiNER     : ['regex', 'entity', 'gliner']
开启领域 NER    : ['regex', 'entity', 'campus_ner']
两个都开        : ['regex', 'entity', 'campus_ner', 'gliner']   ← 两个 NER 模型同时跑，纯浪费
```

**结论：`campus_ner` 整套（模型 388 MB + 中间产物 391 MB + 预训练代码 336 行 + 三个
FreeAL/弱监督实验 1.16 GB）已被 GLiNER 取代。** 它当初是为了补语义识别能力而训的，
现在 GLiNER 在同一任务上更强、更省（21ms vs 576ms）。两者同时开启只会互相干扰。
