# 隐盾 v3 方案：上下文感知的脱敏决策（GLiNER + UIE）

> 状态：方案草稿（待评审）
> 前提：后端 3 任务键 / 身份权限 / 硬约束 / 三边界观测保持不变，本轮只升级「识别 + 决策」两层。

---

## 1. 一句话定位

v2 是「**正则/词典找敏感片段 + TF-IDF+逻辑回归选动作**」——上下文只是拼进特征串里的一个 token，模型并不真正"读"它。

v3 改成「**两个 transformer 真正读上下文**」：

- **GLiNER（双向 NER）** 读句子上下文，判断"这一段是不是敏感信息、是哪一类" → 升级**识别层（m2）**。
- **UIE（schema 驱动的信息抽取）** 读上下文 + 任务的保留契约，判断"哪些必须脱敏、哪些是任务必需可以保留" → 升级**决策层（m4）**。

安全网不动：硬约束（身份证/银行卡/密钥/敏感属性绝对禁止）和三边界泄露观测（m7/m8）照旧，"模型只能选、安全检查只能否决"的原则照旧。

---

## 2. 两个模型的选型结论

| | **GLiNER** | **UIE** |
|---|---|---|
| 干什么 | 通用轻量 NER，零样本 + 可微调 | 通用信息抽取（实体+关系），schema/提示驱动 |
| 结构 | DeBERTa-v3，**双向**（真读上下文） | ERNIE-3.0，中文强 |
| 中文 | `gliner_multi` 系列支持；另有 `gliner_multi_pii` 专做 PII | 中文是其主场，少样本能力强 |
| 体积/速度 | small/base/medium，小、CPU 可跑、可 ONNX | uie-base 约 150M，CPU 偏重 |
| 运行时 | **PyTorch + transformers**（本项目已装） | **PaddlePaddle**（本机未装，Windows 安装摩擦较大） |
| 许可证 ⚠ | 代码 Apache-2.0；**权重 v1 = CC-BY-NC-4.0，v2.x = Apache-2.0** | PaddleNLP / UIE 权重 Apache-2.0 |
| 在本项目里 | **识别层主力**，直接替换现有 RoBERTa `campus_ner` | **决策层抽取**，schema 天然对应 `tasks.yaml` 的 `must_retain`/`never_send` |

**推荐主线**：

- **GLiNER v2.x（`gliner_multi-v2.1` 或社区中文版）** 做识别层 —— 与现有 torch 栈一致、体积小、双向上下文、Apache-2.0 无商用顾虑（务必避开 v1 的 NC 许可）。
- **UIE 做决策层**，把"读上下文判断是否脱敏"这件事交给它的 schema 机制。**风险是 Paddle 运行时**：若 Windows 上 Paddle 太重，备选两条——
  1. 用 HF 上的 PyTorch 移植版 `lvyufeng/uie-base`，绕开 Paddle；
  2. 干脆不用 UIE，用已继续预训练的 `roberta_campus` 接一个序列分类头做决策器（零额外运行时成本）。

> 上线前**逐权重核实 license**（v1 的 CC-BY-NC 会限制商用/成果转化，校园项目若要上云或商用必须用 Apache-2.0 的 v2.x）。

## 3. v3 架构：每个模型落在流水线哪个位置

```
材料/追问
  │
  ▼
m1 访问/权限（不动）
  │
  ▼
m2 识别层（升级）
  ├─ RegexDetector      保留：格式类（手机/邮箱/身份证/银行卡/学号）快、准、可解释
  ├─ EntityDetector     降级：只留表格列名提示，自由文本语义判断交给 GLiNER
  └─ GLiNERDetector     ★ 新增：姓名/机构/地点/敏感属性 的上下文识别
        · 复用 Detector 接口（与 CampusNERDetector 热替换）
        · 输出 Span(category, confidence, detector="gliner")
  │
  ▼
m3 决策层（升级，但硬约束不动）
  ├─ 硬约束 check_hard       保留（绝对禁止项/权限/接收方/低置信）
  ├─ UIE 上下文抽取          ★ 新增：按任务 schema 抽取「需脱敏 / 可保留 / 需删除」
  │     · schema 由 tasks.yaml 的 must_retain/never_send + identity 可读范围动态生成
  └─ 动作映射                把 UIE 抽取结果 → 6 动作；模型只选，安全只否决
  │
  ▼
m6 转换 / m7 外发 / m8 观测（不动）
```

关键点：**格式类继续用正则，模型只补语义类**。13 类里手机/邮箱/身份证/银行卡/学号/密钥/微信/预算/宿舍/成绩用正则已经 100% 且快，强行让模型学反而更慢更不可靠。GLiNER 的价值是姓名/机构/地点/敏感属性这些"看上下文才知道是不是敏感"的类别——正是 v2 词典+停用词表打得最累的地方。

## 4. 数据方案（复用现有资产，不要从零标）

项目里已经有很好的底子，v3 全部复用：

| 资产 | 现状 | v3 用途 |
|---|---|---|
| `data/generated/cases_dev.jsonl` | 合成案例，带 gold_spans | GLiNER 训练集主体 |
| `data/generated/weak_bio.jsonl` | BIO 弱标签（1.4MB） | GLiNER 弱监督预标注 |
| `data/gold/*.json` + `scripts/eval_gold.py` | 人工 gold + 评测 | 评测集 + 留出验证 |
| `data/campus_corpus/*.txt` | 校内公开风格文本 | 弱标注语料 + 扩充 |
| `data/fixtures/*.json` | 三任务样例 | UIE 的 doccano 标注骨架 |

**GLiNER 训练数据**（span 格式 `(start, end, label)`）：
1. 用现有 `RegexDetector` + `EntityDetector` 作**弱标注器**，在 campus 语料上自动标注；
2. 转成 GLiNER 的 span 标注（13 类 → GLiNER label）；
3. 人工 gold 单独留出，**绝不进训练**（现有 `weak_label.py` 的 review 划分逻辑直接复用）。

**UIE 训练数据**（doccano/UIE schema 格式）：
1. 每个任务从 `tasks.yaml` 的 `must_retain` / `never_send` 生成 schema，例如会议纪要：
   `{"需保留的任务事实": ["负责人", "事项", "期限"], "需脱敏的个人信息": ["姓名", "电话", "身份证"], "可公开事实": ["项目名称", "人数"]}`；
2. 用 fixtures + cases 生成标注，UIE 少样本起步，几百条即可见效果。

## 5. 训练方案（本机 RTX 4060 8GB 足够）

- **GLiNER 微调**：装 `gliner` + `peft`，用 **LoRA**（8GB 显存轻松）或小模型全参（`gliner_small` ~ 90M）。
  - 现有 `finetune_ner.py` 是 RoBERTa 的 BIO 训练脚本，可参考其数据加载；GLiNER 有自己的 `model.train()` 接口。
  - 参照文档：<https://docs.knowledgator.com/docs/frameworks/gliner/training/>
- **UIE 微调**：装 `paddlepaddle-gpu` + `paddlenlp`，`Taskflow("information_extraction", schema=...)` → `finetune()`。
  - 若走 PyTorch 移植版，则与 GLiNER 同栈，`Trainer` 即可。
- **评测指标**（必须同时看）：
  - 识别层：13 类 **实体级 F1**（尤其姓名/机构/地点/敏感属性），对比现有正则+词典、现有 RoBERTa `campus_ner`；
  - 决策层：6 动作 macro-F1 + **漏泄召回**（该删没删）优先于精确率——这是隐私项目，宁可多脱敏；
  - 端到端：复用 `data/gold/gold_eval_report.json` 的口径 + 81 pytest + `uishot.js` 回归。

## 6. 推理与集成

- **热替换**：`GLiNERDetector` 实现与 `CampusNERDetector` 完全相同的 `Detector` 接口，权重放 `models/gliner`，`.env` 加 `SHIELD_USE_GLINER=true` 开关。模型不可用/推理失败 → 按现有 `DetectionError` 暂停或回退规则底座（现有 `build_detectors` 的多检测器 + `merge_spans` 优先级机制直接复用）。
- **延迟预算**：现有 `campus_ner` 因 576ms 默认关闭。GLiNER 走 ONNX（`onnxruntime` CPU）目标压进 **≤ 200ms/段**；不行就小模型 + 批处理 + 异步。格式类仍由正则即时处理，模型只跑语义类子集。
- **决策层**：UIE 输出只进 `necessity_scorer` 的**上下文表示**，动作仍由 `decide_segment` 统一裁决，硬约束 `check_hard` 保持最后一道闸。

## 7. 里程碑与工作量（粗估）

| 阶段 | 内容 | 产出 | 估时 |
|---|---|---|---|
| **M0 骨架+基线** | 装 gliner/peft/onnxruntime；GLiNER **零样本**跑现有 13 类，量 F1/延迟 | 零样本基线报告 | 0.5–1 天 |
| **M1 数据** | 弱标注 + 人工 gold 扩充，产出 GLiNER span 集 + UIE schema 集 | `data/ner_v3/*` | 1–2 天 |
| **M2 GLiNER 微调+接入** | LoRA 微调 → `models/gliner` → `GLiNERDetector` 接入 m2 → 评测 | 识别层 v3 | 2–3 天 |
| **M3 UIE 决策** | UIE/PyTorch 版微调 → 接 m4 决策 → 评测 | 决策层 v3 | 2–4 天 |
| **M4 上线** | ONNX/CPU 优化、全量回归、前端可选开关、文档 | 可切换的 v3 | 1–2 天 |

总计约 **1.5–2 周**（一人，含调试余量）。

## 8. 风险与待决策（开工前确认）

1. **许可证（最高优先级）**：GLiNER **v1 是 CC-BY-NC-4.0**（禁止商用），**v2.x 是 Apache-2.0**。若项目可能商用/成果转化，必须锁定 v2.x 并逐个权重核对；UIE/PaddleNLP 是 Apache-2.0，但 HF 移植版的 license 也要看 README。
2. **Paddle 在 Windows 的摩擦**：UIE 默认要 PaddlePaddle，Windows + 8GB 的 GPU 版安装常有坑。**我的建议**：先上 GLiNER（torch 栈，零摩擦），UIE 决策层若 Paddle 不顺就用备选（PyTorch 移植版 / roberta_campus 分类头），别让运行时绑架进度。
3. **数据量是否够**：13 类中语义类（姓名/机构/地点/敏感属性）的标注最贵。先让 GLiNER 零样本跑一遍（M0），看它在现有 gold 上已经能到什么水平——零样本够用就先只做决策层。
4. **上下文到底多长**：GLiNER/UIE 单次只读 ≤512 token（句子/段内）。跨句、跨文档的"上下文"需要滑窗或文档级方案。**先做句子级**，够用再扩展，不要一上来就上长上下文模型。
5. **模型 vs 规则的分工别搞反**：格式类让正则继续管（更快更可解释），模型只管语义类；这个边界要在评测里显式守住，避免"模型为了学手机号正则反而变慢"。

---

## 9. 与 v2 思路的差异（应你的要求，不跟着第二版走）

| 维度 | v2 | v3 |
|---|---|---|
| 识别 | 正则 + 姓氏/后缀/停用词启发式 + 可选 RoBERTa | GLiNER 双向上下文识别语义类 |
| 决策 | TF-IDF + 逻辑回归（token 拼串） | UIE schema 抽取 / 上下文分类头 |
| "上下文" | 只是特征串里的一个 `[CONTEXT]` token | 真正被模型逐 token 读进去 |
| 数据 | 合成弱监督为主 | 复用现有弱标签 + gold，少样本即可起步 |
| 安全网 | 硬约束 + 三边界观测 | **不变** |
