# 隐盾 LLM-Shield · 项目现状与系统架构总览

> 生成时间：2026-10-16 · 对应 v3 阶段（GLiNER A 层已落地）

---

## 0. 一句话定位

**本地隐私防护网关**：材料只在本机完成「识别 → 决策 → 转换」，云端大模型**只收到脱敏后的文本**；
全过程在三个边界上做泄露观测，任何不确定都倾向暂停外发。

技术栈：Python + FastAPI（后端）、原生 HTML/CSS/JS（前端，无构建步骤）、
规则/词典 + GLiNER 神经模型（识别）、TF-IDF+LR（动作决策）。

## 2. 数据流

```
用户消息/材料
   │
   ▼
① m1_access   身份过滤（readable）→ 权限检查（can_send_to）
   │
   ▼
② m2_detect   ┌─ RegexDetector    格式类（电话/邮箱/证件/银行卡/学号/密钥/微信/预算/成绩）
              ├─ EntityDetector   词典类（姓名/机构/地点/敏感属性/列名）
              ├─ GLiNERDetector   v3 神经语义（13 类，两趟推理）★本会话新增
              └─ CampusNERDetector 可选（默认关）
                    ↓ merge_spans 合并（同类别取高置信精确边界；跨类别取并集+更严格类别）
                    ↓ segmentize 按句切分 → attach_spans 挂载 + 填上下文窗口
   │
   ▼
③ m3_decide   ④ 动作模型 argmax(6 动作) → 硬约束校验（失败→PAUSE，不降级）
   │
   ▼
⑤ m5_utility  效用提示（advisory）
   │
   ▼
⑥ m6_transform 按动作改写文本（含会话内稳定代号映射）
   │
   ▼
⑦ m7_egress   三边界检查 → 云端模型（只收到脱敏文本）
   │
   ▼
⑧ m8_audit    B1 模型输入 / B2 用户展示 / B3 工具外发 —— 以实际载荷判定是否泄露
```

## 3. 配置驱动（`config/*.yaml`）

### 3.1 `rules.yaml` —— 14 类敏感类别 + 6 动作

| 类别 | kind | level | hard_ban |
|---|---|---|---|
| PHONE / EMAIL / ID_CARD / BANK_CARD / STUDENT_ID / API_KEY / WECHAT / BUDGET / DORM / GRADE | format | 2~4 | ID_CARD·BANK_CARD·API_KEY |
| PERSON_NAME / ORG / LOCATION / SENSITIVE_ATTR | semantic | 1~4 | SENSITIVE_ATTR |

**动作与披露代价**：DELETE 0 < LOCAL_AGGREGATE 1 < GENERALIZE 2 < PSEUDONYMIZE 3 < RETAIN 5 < PAUSE 99

**硬约束**：`absolute_ban = [ID_CARD, BANK_CARD, API_KEY, SENSITIVE_ATTR]`；
低置信（<0.60）且高风险（level≥4）禁止任何外发；未知接收方一律 deny。

### 3.2 `tasks.yaml` —— 3 个任务模板（后端契约，仅 3 个 key）
`activity_stats` / `meeting_minutes` / `project_intro`，各自定义 `must_retain`、`never_send`、`prefer`。

### 3.3 `identities.yaml` —— 3 个身份
| 身份 | readable | max_level | can_restore |
|---|---|---|---|
| student_leader | activity_roster, meeting_minutes, project_plan, uploaded | 3 | ✔ |
| course_member | meeting_minutes, uploaded | 2 | ✘ |
| external_partner | project_intro_draft, uploaded | 1 | ✘ |

### 3.4 `recipients.yaml` —— 6 个接收方（对应三边界）
- **B1 外部模型**：`external_model`（trust=low, max_level=2）
- **B2 查看者**：`viewer_teacher`(high/4) / `viewer_peer`(medium/2) / `viewer_outside`(low/1)
- **B3 工具端**：`egress_tool_public`(low/1) / `egress_tool_internal`(medium/3)

## 5. ★ 识别层现状（v3 重点，本会话成果）

**当前默认组合：正则 + 词典 + GLiNER v3（三路并行 + 合并）**

### 5.1 三路分工

| 检测器 | 负责类别 | 边界 | 说明 |
|---|---|---|---|
| **RegexDetector** | 格式类（9 类） | 精确 | 带校验位：身份证 GB 11643、银行卡 Luhn |
| **EntityDetector** | 姓名/敏感属性/列名（+可选机构/地点） | 偏宽 | GLiNER 激活时**关闭机构/地点**（贪婪正则会框入引入词） |
| **GLiNERDetector** | **除身份证外 13 类** | 精确 | v2.1 微调，**两趟推理**（语义 5 标签 + 格式 8 标签）|

### 5.2 三个关键工程决策（都有实测支撑）

1. **字符级中文分词**（`char_splitter.py`）：GLiNER 默认 whitespace 分词把整串中文当一个 token，
   实体边界系统性错位。换成 char-level 后零样本 F1 从「几乎检不出」→ 0.594，微调后 0.946。
2. **两趟推理**：13 个标签一起推理时标签竞争会稀释稀疏类别（敏感属性）分数导致漏检；
   拆成 5+8 两趟后恢复。代价：延迟 ~2 倍（单条短文本 ~43ms，仍远低于 500ms 预算）。
3. **合并策略**（`merge_spans`）：
   - 同类别重叠 → 取**置信度更高者的精确边界**（不再强制取并集，否则词典的宽边界会盖住模型精确边界）
   - 跨类别重叠 → 取并集 + 更严格类别（安全优先，不丢原文）
   - 冲突优先级含**检测器可信度（正则 > 模型）**：正则以 GB 11643 核验的身份证，
     不能被 GLiNER 的"高置信猜测"覆盖

### 5.3 性能与效率

- 检测器（GLiNER / CampusNER）为**模块级单例缓存**：首次加载 ~8.6s，之后复用
  （此前每次请求都重载 1.1GB 模型，是严重效率 bug，已修）
- 单条短文本识别延迟 ~43ms；长文本按 `max_len-32` 滑窗

### 未完成（v3 后续）
1. **单对话框**（S2）：`task`/`recipient` 从对话推断；`identity` 移出对话（授权边界不可自述）
2. **跨轮会话状态**（S3）：别名一致、累计计数、歧义指代 → PAUSE
3. **细粒度决策**（S4）：备份里的 `decision_v2.py` 支持「同段内姓名假名化 + 电话删除」，
   当前 `decision.py` 每段只有一个动作（信任门槛已内联在 `constraints.py`，没有丢失）
4. **组合式重识别**（S5）：`avoid_unique_award_linkage`

### 已知短板
- GLiNER 在**字母数字串类目间**仍有边界模糊（敏感属性 8 FP、地点漏检等），新留出集 F1 0.9382
- 新测试集与训练数据**同源生成器**，0.9382 含有"拟合生成器风格"的成分，不等于真实文本表现
- 旧备份 `.backup_20261014/` 里有更完整的决策层（`decision_v2` / `retain_policy` /
  `necessity_verdict` / `eval/` 消融框架），尚未迁移

### 环境依赖（重要）
- `transformers` 必须 **4.x**（5.x 的 DebertaV2Tokenizer 只认 native 格式、不读 spm.model）
- 当前：transformers 4.57.6 + datasets 3.6.0 + gliner 0.2.29
- Windows 下 GLiNER `train_model` 需 `dataloader_num_workers=0`
