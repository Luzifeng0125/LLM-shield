# 程序优化记录（2026-10-16 至 17）

## 处理流程

`processing.analyze()` 现在由对话、预览和单次运行共同调用，负责任务与权限检查、模型就绪检查、逐份材料识别和动作决策。`material_processing` 保留每份表格的列与行上下文，把敏感片段转换为拼接文本中的统一坐标。含不同敏感类别的同一句会按实体边界拆成互不重叠的决策片段；未识别文本仍按原顺序保留。任何片段选择暂停或违反硬约束，整轮停止外发。

转换仍使用本地映射。对话把本轮暂存的会话代号显式交给外发网关；复检仅豁免载荷中这些代号所在的准确位置，不再读取跨会话全局映射。单次运行每次使用独立映射，避免用户提供相同 `session_id` 时复用另一请求的原值。

## 运行与观测

- `/api/health` 返回动作模型、识别器、真实 API 配置和会话容量状态，不返回密钥或模型路径。
- `/api/metrics` 只统计阶段耗时；每项最多保留最近 500 个数值，返回中位数和 P95。
- 本地识别与决策并发上限由 `SHIELD_MAX_PARALLEL_ANALYSES` 配置，默认 2，范围 1–8；满载时请求暂停并提示重试。
- 模型单例创建加锁，避免并发请求重复加载权重。过期和删除会话时清除历史、敏感片段与代号映射；服务退出时清除进程内会话。
- 多份材料的 GLiNER 滑窗合成一批推理，仍按材料还原坐标；每批最多 16 个窗口。推理异常会暂停请求，不再被当成“没有命中”。
- 浏览器显示本地就绪状态、处理中和等待回答状态；暂停时给出对应的重试建议。
- 模型目录默认项目内 `models/`。GLiNER 仍需用 `SHIELD_MODEL_DIR` 指向纯 ASCII 路径；`.env.example` 默认关闭 GLiNER，显式开启时安装 `requirements-gpu.txt`。

## 验证

运行 `python scripts/run_checks.py --rules-only` 和启用 GLiNER 的 `python scripts/run_checks.py`：两种模式均为 123 个测试、31 个子检查、38 项冒烟通过。启用模型后的 2000 字冒烟识别耗时约 192 ms，低于该测试的 500 ms 阈值。

`python scripts/benchmark_local.py --repeats 5` 在本机启用 GLiNER 后测得：短文本中位数 25.09 ms、三份材料 27.78 ms、约 2000 字材料加长历史 427.14 ms。三份材料在批量推理前的中位数约 131.54 ms；两次测量样本数不同，只表明明显下降，不能当作严谨的加速比。长材料此次最大值 492.66 ms。样本仍很少，这些数值不当作生产 P95；`/api/metrics` 可用于收集实际请求的阶段耗时。

使用固定公开短句执行一次真实 API 连接检查：连接成功，响应 2 字符，耗时 1762 ms。随后用公开讲座文本执行一次完整流水线：模型输入和查看边界通过，公开工具边界按自身策略拦截，整个请求未暂停。没有发送用户材料。

人工标注材料上的识别准确率、决策质量及并发负载仍需单独验收。系统身份选择目前是界面配置，并非生产级身份认证；若面向多人部署，需要接入可信身份源和持久化会话存储。
